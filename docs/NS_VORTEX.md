# 三维 NS 涡旋可视化（模式 A′：前导阶自相似解）

> 目标：把「Navier–Stokes 涡旋内旋、轴向拉伸、有限时间奇异性演化」做成 PlotKit 里一个**由真实场驱动**的三维可视化模块，而不是演示动画。
> 状态：2026-11-01 首版。渲染 98–120 fps，诊断与公式同屏，参数可实时调。

## 1. 数学来源与模式声明

- 论文：**Finite time blowup for Navier–Stokes**（2026-09-08，166 页，附 Lean 形式化仓库 `openai/NavierStokesAndEuler`）。§3.1 给出显式相似坐标，剖面 `E/U` 由 §4 隐式构造，**没有闭式解**。
- 本模块实现的是 **A′：前导阶相似场复现**。相似坐标与标度照搬论文：

```
τ = 1 − t
r = √(2qX)              z = q^{1/2−h} η
q = τ / (1 − η²)
u_θ = q^{−(1/2+h)} E(X, η)
u_z = q^{−(1/2+h)} U(X, η)
u_r = V₀(X) / r         （由不可压条件积出）
‖u‖_L∞ ~ τ^{−(1/2+h)}   ‖ω‖_L∞ ~ τ^{−1}
```

- 剖面（论文没有闭式，这里自选并**显式标注**）：

```
E = c∞ · sech²(η/η₀) · √X / (1 + (X/X₀)^{h+1})
U = c∞ · α · η · sech²(η/η₀) · √X / (1 + (X/X₀)^{h+1})
```

近轴 `E ≈ c∞√X`（轴上光滑，无 1/r 奇点），远场 `E ~ X^{−1/2−h}`（与论文尾部一致）；`U ∝ η` 保证 `z=0` 两侧轴向速度反向。
**不复现**：环带脉冲初始数据、光滑紧支外力（论文 §4 的构造工具），因此本模块**不声称**给出爆破解。

界面左下常驻标注：`Mode A-prime - Leading-order similarity field (not a verified blow-up solution)`。

## 4. 实测

场（`SimilarityParams()`，`h=0.005`）：

| 量 | τ=0.2 | τ=0.05 | τ=0.02 | τ=0.005 |
| --- | --- | --- | --- | --- |
| `u_max` | 0.840 | 1.834 | 2.909 | 5.818 |
| `ω_max` | 9.72 | 39.1 | 98.0 | 391.4 |
| 涡核半径 | 0.350 | 0.321 | 0.204 | 0.103 |

- 轴上角速度 `Ω = u_θ/r` 在 `r = 1e-4 … 1e-2` 恒定 → 刚体旋转核，无 1/r 奇点。
- 不可压残差 `‖∇·u‖/‖u‖`：t=0.2/0.5/0.9 → **2.5% / 2.3% / 2.1%**。
- 标度自洽：`u_max` 比值 6.9 ≈ 40^0.505，`ω_max` 比值 40.2 ≈ 40^1.0。

渲染（1280×820 窗口，2217×1372 canvas）：**98–120 fps**；粒子 24 000；体积 raymarch 每像素最多 220 步。

## 5. 已知限制

1. **不是爆破解**：只复现前导阶相似结构；论文的环带脉冲与紧支外力未实现，`h` 的严格区间是 `0<h<1/100`（界面放宽到 0.5 仅作视觉演示，`paper_compliant` 会标注）。
2. **剖面是自选的**：论文的 `E/U` 是隐式构造，没有闭式解，本模块用的是「sech² 核 + 幂律尾」近似族。
3. **视觉与参考视频有差距**：参考图那种「细亮丝 + 湍流状纹理」来自更陡的径向剖面与更多粒子；本场是光滑轴对称解，观感是「发光柱 + 螺旋粒子流」。
4. 网格列的散度残差（0.26）明显大于解析列（0.03），这是方位角离散误差，面板已如实展示。

## 12. 视觉调优（2026-11-01，对齐参考视频）

参考目标是「黑底 + 赤道同心环盘 + 橙色轴向柱 + 亮核」。要复现它，问题不在着色，而在**示踪粒子的撒点方式**：

| 现象 | 根因 | 做法 |
| --- | --- | --- |
| 一开始只是一根「实心棕柱」 | 体积遮罩用 `length(p.xz)`/`abs(p.y)`，而场以 **z 为轴** | 遮罩、条纹坐标、播种全部改回 `p.xy` / `p.z` |
| 看不出同心环 | 粒子在半径上连续均匀撒 | 撒在 **26 个离散壳**上（`r = rMax*(shell+0.5)/26`，±1.5% 抖动） |
| 跑几秒就糊成白团 | 这个场是**向轴收缩**的，示踪粒子迟早堆进核心 | 按注入式回收：寿命到、飞出域、或 `r < 5% rMax` 时重新撒回壳上 |
| 环发白、没有层次 | 12 万点加法混合过曝 | 每点 `a = core*(1-0.25*age)*0.05`，点径 3.2 px |
| 颜色全橙 | 早期按 |u| 着色（轴上最快） | 改**按半径**着色：`r/rMax<0.25` 白橙 → `<0.55` 橙 → 外圈蓝紫 |

对应旋钮（页面右侧）：体积密度、粒子数（2 万–30 万）、光柱随流强度、螺旋缠绕；相机默认 `pitch 0.42 / dist 3.6`（太平看不出环是圆的）。

实测（2217×1372 canvas）：**48–63 fps**（20 万粒子 + 体积 raymarch）。

## 13. 三项观感补齐（2026-11-01）

| 目标 | 做法 | 代价 |
| --- | --- | --- |
| **辉光（bloom）** | 场景先渲到离屏纹理 → 亮部提取（阈值 0.92 + knee）→ 1/2 分辨率分离高斯（横/纵各 9 tap）→ 加法合成；页面加「辉光强度」滑条 | 每帧多 4 个 pass，1280×820 下约 3 ms |
| **环更细更匀** | 环不再靠粒子撒点，改成**几何圆环层**：40 条等半径壳各 160 段 `gl.LINES`，颜色按半径取同一套调色板，加法混合 | 12800 个顶点，可忽略 |
| **柱的颗粒喷射** | 赤道盘/轴柱比例 78%/22%，轴柱粒子按真实 `u_z` 平流并按高度错开寿命，点径 3.2、单点 alpha 0.075；体积解析条纹降为辅助 | 无 |

新增 uniform/旋钮：`uAlpha`（环亮度 0.22）、`bloom`（0.45）、`bloomThresh`（0.92）、`ringAlpha`。
实测 **39–55 fps**（12 万粒子 + 体积 raymarch + 4 个后处理 pass，2217×1372 画布）。

## 14. 相机预设与外圈亮度（2026-11-01）

- **俯视环盘（`btn-top`）**：`yaw=-π/2, pitch=1.33, dist=2.55`。`pitch` 是仰角，视锥里环盘的短轴/长轴比 ≈ `sin(pitch)`：默认 0.62 时只有 0.58（椭圆），1.33 时 0.97（近似正圆）。这就是「参考图环是正圆、我们默认是椭圆」的全部原因，改的是机位不是数据。
- **侧视（`btn-side`）**：`pitch=0.10`，用来看轴向拉伸与上下收细的锥。
- **默认视角（`btn-reset`）**：`pitch=0.62, dist=3.1`（3/4 视角，兼顾环盘与柱体）。
- **外圈蓝紫层次**：该自相似场在 `r>0.35` 时 `Ω` 已经很低，再往外是纯几何壳、没有场强可依，所以环的颜色/亮度改为**按壳序号**给（`a = 0.55 + 0.95·r/rMax`，外圈更亮），不再依赖场强。实测俯视帧里蓝紫像素占比 31.6%、暖色 41.3%（此前外圈几乎不可见）。
- 截图：`docs/ns_vortex_top.png`（2217×1442，47 fps）。

## §15 矢量箭头层与播放控制（2026-11-01）

- 后端 `GET /api/ns/arrows?t=&n_r=&n_theta=&n_z=`：柱坐标稀疏网格（默认 7×20×6 = 840 支），返回 `位置 xyz + 速度 xyz`（float32，同一二进制帧格式）。
- 前端箭头层：方向严格取真实速度（`u_r/u_θ/u_z` 旋转到笛卡尔），长度 ∝ |u|（0.35–1.0 倍基准长），颜色按半径（内圈暖橙 / 外圈蓝紫）；「矢量」按钮可整层关闭，「箭头长度」滑条即时生效。
- 粒子约束持续性：单步位移上限 `2%×ext`，超过就自动切子步（最多 6 步），配合 τ^0.55 的自相似步长，τ→0 时不再越界重撒。
- 播放倍速：0.5×–8×，底层 `S.rate × 0.02 × t_blow` 每秒推进；实测 6× 时 2 s 里 t 前进 0.243（≈0.12/s）。

## §16 参数快照、动画导出与相似坐标（2026-11-01）

- **快照对比**（Q8）：「快照」按钮冻结当前 `h/X₀/η₀/t` 的画布缩略图 + 诊断值（ω_max、|u|_max、涡核半径），列在右下角面板；点任意一条即恢复那组参数与时刻并重绘。
- **导出 GIF/MP4**（VortexExporter）：前端按 `t=0.02→0.98` 扫 24 帧（`?gifn=` 可调），逐帧 `canvas.toDataURL('image/jpeg',0.85)` 后 POST `/api/ns/export`；服务端用 PIL 合成 GIF，或调 ffmpeg 出 MP4（缺 ffmpeg 时明确报错）。实测 6 帧 → 415 KB GIF；4 帧管线 86 KB。导出期间自动暂停并在结束后恢复原时刻。
- **相似坐标 ξ**：「ξ 相似」按钮按自相似长度 `L(τ)=τ^(1/2+h)` 缩放相机视距（`zoomScale=(0.5/τ)^(0.5+h)`，夹在 0.5–12），让涡核在屏幕上保持同样大小，便于看内部结构。实测 t=0.9 → 2.25×、t=0.2 → 0.79×。

## §17 速度网格协议与显示一致性修复（2026-11-01）

- **`/api/ns/velocity` 轴序**：元数据承诺 `x fastest, then y, then z`，但旧实现直接 `ravel()` 形状 `(x,y,z)` 的数组，实际是 z-fastest；前端 `_advect` 按 `(i + j*n + k*n*n)*3` 取样，于是粒子的径向/轴向速度被互换，出现“只会向外散/原地冻结”的观感。现在服务端按 `order="F"` 展开，并把每个格点的 `u,v,w` 交错成 AoS，与前端 `idx*3+c` 完全一致；回归测试 `test_velocity_frame_preserves_declared_xyz_order` 用解析 `velocity_at` 校验已知非对称点。
- **速度域覆盖**：切片/粒子域是 `r≤0.5, |z|≤1.2`，旧速度请求只有 `0.35/1.0`，边缘粒子落在无速度区会冻结到重撒。页面现在请求同一物理域（`extent=0.5&z_extent=1.2`）。
- **尾迹半径 uniform**：`nsview.js` 把数组 `this.extent` 当对象读 `this.extent.x`，得到 `undefined`，尾迹着色器 `uRMax` 失效。改为 `this.extent[0]`。
- **相似坐标缩放**：场域变化时旧代码用径向比例同时缩放粒子的 x/y/z；现在 z 使用 `z_max` 自己的比例，径向与轴向分别换算。
- **网格诊断**：`grid_stats()` 的 `np.gradient` 原来对 x/y/z 统一用 `h`，但 API 的 z 域是 `z_extent`，z 导数被系统性放大；现在按 `(h,h,hz)` 求导，体元改为 `h*h*hz`，散度复用 `dW_dz`，涡核半径改为从轴心 `mid` 起算。
- 验证：`PYTHONPATH=src python -m pytest tests/test_ns_field.py tests/test_ns_api.py -q` → 25 passed；`node --check src/plotkit/static/nsview.js` 通过；`--shot` 截图见 `docs/ns_after_fix.png`（t=0.95，41 fps，速度网格已加载）。

## 17. 模式 B：真数值解（伪谱 NS 求解器）

`src/plotkit/ns/solver.py` —— 参考 [cmccomb/navier-stokes-singularity-simulation](https://github.com/cmccomb/navier-stokes-singularity-simulation) 的实验设定，在本机用纯 NumPy 实现了一个**三维不可压 NS 伪谱求解器**，作为"数值解"数据源（模式 B）。

### 17.1 数值方法

| 环节 | 做法 |
| --- | --- |
| 空间 | 三维周期立方体 `[0,L)³`，`N³` 网格（默认 32³），伪谱（FFT） |
| 非线性 | `(u·∇)u` 在物理空间中心差分 → 回谱空间，**2/3 去混叠** |
| 时间 | Heun RK2 + 每步投影（`k·û = 0`） |
| 外力 | 从静止起步，`tanh` 平滑开启的轴对称旋涡力：角向 `(-y,x,0)/r` + 轴向 `sign(z)|z|/σ_z`，三个高斯脉冲（中心 0.20/0.45/0.72，权重 1.0/1.6/2.4） |
| 步长 | 自适应 `dt = min(dt₀, 0.35·dx/v_max, 0.4·dx²/ν)` |

默认参数：`n=32, L=2.0, ν=4e-3, t_end=0.95, save_every=0.02`。

### 17.2 实测

| 规模 | 耗时 | 帧数 | 内存 |
| --- | --- | --- | --- |
| 24³ / t=0.6 | 2.8 s | 13 | 3 MB |
| 32³ / t=0.95 | **13.8 s** | 48 | 18.9 MB |

峰值速度 0 → 0.016 → 0.091 → 0.207 → 0.243 → **0.444**；峰值涡量 0 → 0.574 → 3.02 → 6.82 → 7.31 → **13.6**；散度 ~1e-17（谱投影精确）。

### 17.3 两个真 bug

1. `nonlinear()` 把谱系数当物理量又做了一次 `fftn` → 双重变换，`t>0.15` 即 overflow。修法：入参就是谱系数，内部 `ifftn` 回物理空间算对流项再 `fftn`。
2. 固定 `dt=0.006` 在强外力下违反 CFL → 发散。修法：按 `v_max` 与粘性算自适应步长。

### 17.4 接口与用法

所有 `/api/ns/*` 端点都接受 `source=analytic|solver`：

```bash
python -m plotkit.ns.app --source solver          # 首次约 15 s 出解，页面显示进度
python -m plotkit.ns.app --source solver --t 0.6 --shot b.png --seconds 45
```

数值解模式下 `h/X₀/η₀` 三个旋钮被禁用（数值解不吃剖面参数），面板脚注改为「有限时间代理，非奇异性证明」。

> **诚实声明**：32³ 的数值解只能说明"涡量在快速增强、散度保持机器精度"，**不构成有限时间奇异的证明**。参考工程自己在 README 里也写明 *finite surrogate, not an independent proof*。

瓶颈不在 GPU 绘制，而在 **JS 侧的粒子推进**：每帧对每个粒子做三线性采样 + RK4 子步（`_advect`），1M 粒子 = 每帧数百万次采样。任务书要求的 500 万向量在当前架构下做不到，必须把推进搬到 GPU（transform feedback / 速度纹理 ping-pong），这是下一步而不是调参能解决的。

### 18.1b 已完成的三项调优（2026-11-01）

| 改动 | 做法 | 效果 |
| --- | --- | --- |
| 子步预算随规模收缩 | `subCap = 40 万以上 1 步 / 15 万以上 2 步 / 其余 6 步` | 大粒子数下不再跑 6 次 RK2 |
| 顶点预算 LOD | 流线每 `ceil(n/150000)` 挑一条、点精灵每 `ceil(n/200000)` 挑一个 | 100 万粒子从 800 万顶点降到 120 万，避免纯 GPU 端爆掉 |

| 暂停/继续 | 播放→暂停→继续→暂停，比较物理时间 | ✅ 只前进不跳回 |
| 相机不改数据 | 拖动旋转后比较诊断 | ✅ 一致（测试前先暂停，否则 diag 本就随时间变） |

> 说明：本页的物理状态由 `t`（滑条）参数化，而不是"从 t=0 积分到现在"，所以倍速/跳转天然不会改变物理量——这一点和 `AnimationController` 的设计一致（仿真时间与渲染时间解耦）。

### 18.3 流线层（本版新增）

粒子在纹理里保存 **8 帧历史位置**（`[slot][row][col]` 布局，宽 1024，RGB32F），顶点着色器 `texelFetch` 取出后画成 instanced `LINE_STRIP`，头部亮、尾部按 `(1-age)²` 淡出。代价：120k 粒子约 11.6 MB 纹理、每帧一次 1.4 MB 行块上传、帧率 31→29 fps。

### 18.1c 「JS 减负」：把 CPU→GPU 上传砍下来（2026-11-01）

粒子规模的真实瓶颈不是推进数学，而是**每帧把整份粒子数组传给 GPU**：50 万粒子时
`positions + prev + colors + age` 约 18 MB/帧，WebView2 的 `bufferSubData` 只能跑到
百来 MB/s，帧率直接掉到 9 fps。

三项改动（都在 `src/plotkit/static/nsview.js`）：

| 改动 | 做法 | 效果 |
| --- | --- | --- |
| 轮转更新 | `frac = count>400k ? 3 : (count>150k ? 2 : 1)`，每帧只推进 1/frac 的粒子，`age` 按 `frac` 补偿 | CPU 推进成本 ÷frac |
| 颜色按需上传 | 颜色本来就每 4 帧才重算，改成只在算过的那帧 `bufferSubData(P.cbo)` | 省 ~6 MB/帧（50 万） |
| 拖尾按需上传 | `settings.trail === 0` 时不传 `prev` | 关拖尾省 ~6 MB/帧 |
| 显示 LOD 收紧 | 点精灵 12 万、流线 10 万顶点上限；>20 万时残影层 3 → 2 | GPU 顶点处理恒定 |

实测（2217×1372，体积+环+流线全开，等 12–15 s 初始化后读数）：

| 粒子数 | 改动前 | 改动后 |
| --- | --- | --- |
| 12 万 | 48–58 fps | 41–49 fps |
| 50 万 | 10 fps | **29 fps** |
| 100 万 | 5–6 fps | **15 fps** |

结论：**上传带宽**是这条路的墙。要继续往上（任务书的 500 万）必须让位置留在显存里
（GPU 推进 / transform feedback），仅靠 JS 侧减负到 100 万就到头了。
